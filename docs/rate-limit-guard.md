# AI APIコスト暴走ガード（レート制限）設計メモ

P0第1段階として、サーバー側でAI実行APIに短時間レート制限と日次使用上限を適用した。
実装本体は `src/lib/ai/rate-limit.ts`。

## 対象エンドポイント

- `POST /api/investigations/[id]/run`（3AIプロバイダー並列調査+ナレーション生成。
  最もコストが高い経路）— 認証必須。ガードは認証後・実行前に適用。
- `POST /api/assistant`（AI相談室チャット）— 未ログインでも利用可能なため、
  匿名利用の識別単位も必要。

対象外（意図的にスコープ外）:
- `GET /api/ai/health`（管理者専用の疎通診断。モデル選定・ヘルスUI領域のため
  本タスクのスコープ外として変更していない）。

## 識別単位

- 認証済み利用者: セッションのメールアドレス（`getSessionEmail()`、正規化して小文字化）。
- 匿名利用（`/api/assistant`のみ）: `x-forwarded-for`（先頭IP）または`x-real-ip`から
  取得したクライアントIPをsha256でハッシュ化した値。IPを一切取得できない場合は
  匿名利用者共通の固定バケットにフォールバックする（無制限化を防ぐため）。

### なりすまし対策と残存リスク

- 生IPは保存・比較せず、常にハッシュ化した値のみをバケットキーに使う。
- `x-forwarded-for`はクライアントが任意の値を送れるヘッダーであり、アプリ自身は
  「どのプロキシホップを信頼するか」を検証する手段を持たない。本番でVercel等の
  信頼できるリバースプロキシ/CDN配下で運用され、そのプロキシが末端クライアントの
  IPを`x-forwarded-for`の先頭に正しく設定する構成であることを前提とする。
- 悪意ある匿名クライアントがヘッダーを詐称してIPを毎回変える場合、匿名バケット単位の
  上限は個々には回避され得る（＝完全な水も漏らさぬなりすまし防止ではない）。これは
  新規の認証基盤やWAF/CAPTCHA等を追加しないP0段階での現実的な妥協点であり、
  既知の残存リスクとして明記する。認証済み経路（調査実行API）はメールアドレス単位
  のため、この制約を受けない。

## 制限方式（固定窓 / fixed window）

各リクエストで以下の2種類のカウンタを消費する（両方をこの1回の呼び出しで判定）:

1. 短時間窓制限: `AI_RATE_LIMIT_WINDOW_MS`（既定60秒）ごとに、認証済み利用者は
   `AI_RATE_LIMIT_MAX_PER_WINDOW`（既定5回）、匿名利用者は
   `AI_RATE_LIMIT_ANON_MAX_PER_WINDOW`（既定2回）まで。
2. 日次上限: UTC日付基準で、認証済み利用者は`AI_RATE_LIMIT_DAILY_MAX`（既定50回）、
   匿名利用者は`AI_RATE_LIMIT_ANON_DAILY_MAX`（既定8回）まで。

いずれかを超えた場合、HTTP 429を返し、`Retry-After`ヘッダーで次に試行可能になる
までの秒数を返す。レスポンス本文には利用者向けの安全なメッセージのみを含み、
APIキー・内部例外・他利用者の使用量は一切含めない。

環境変数が未設定・不正な値（数値でない、最小許容値未満）の場合は警告ログを出し、
安全な既定値にフォールバックする（機能が無効化されたり無制限になったりしない）。

## 永続化と水平スケール

- `DATABASE_URL`が設定されている場合、新規テーブル`ai_rate_limit_buckets`
  （`bucket_key` PK, `count`, `expires_at`, `updated_at`）にPostgresの
  `INSERT ... ON CONFLICT DO UPDATE`で原子的にカウントを増加させる。
  バケットキーには「識別単位＋窓の種別＋窓インデックス or 日付」を含むため、
  窓が変わると新しい行になり自然にリセットされる。行ロックによる原子的な
  increment のため、複数インスタンスが同一DBを参照する水平スケール構成でも
  カウントは正しく共有される。
- `DATABASE_URL`が未設定（ローカル開発等、既存コードの`repository.ts`と同じ
  フォールバック方針）の場合はプロセス内メモリのMapにフォールバックする。
  **この場合、インスタンスごとに独立したカウントになり、複数インスタンス環境
  では制限が正しく共有されない**（P0の既知の限界）。本番でAI呼び出しコストを
  厳密に制御する必要がある場合は、`DATABASE_URL`を設定したPostgresバックエンドの
  利用を前提とすること。

## 残存リスク・今後の改善候補

- 匿名利用のIPベース識別は、ヘッダー詐称や共有IP（NAT配下の複数利用者が同一IPを
  共有するケース）に対して完全ではない。将来的にはCAPTCHA・デバイスフィンガー
  プリント・別途の匿名トークン発行などの強化を検討する。
- `ai_rate_limit_buckets`テーブルは行が時間経過で増え続ける（短時間窓は最大で
  利用者数×1日あたりの窓数、日次は利用者数×日数）。P0では明示的なクリーンアップ
  ジョブを追加していない。運用が進んだら`expires_at`を使った定期削除
  （例: 日次バッチでの`DELETE ... WHERE expires_at < now() - interval '7 days'`）
  の追加を推奨する。
- 固定窓（fixed window）方式のため、窓境界をまたぐ直前直後に短時間で集中すると
  理論上は窓あたり上限の最大2倍近いリクエストが通る可能性がある（スライディング
  ウィンドウではないため）。P0の簡易実装として許容し、必要になれば
  スライディングウィンドウ/トークンバケット方式への強化を検討する。
