## 1. 現状調査結果: 削除機能は全レイヤーで完全に欠落している

コード全体を確認した結果、案件削除機能はUI・API・サービス層のいずれにも存在しない。

| レイヤー | 調査箇所 | 結果 |
|---|---|---|
| APIルート | `src/app/api/cases/[id]/route.ts` | `GET`/`PATCH`のみ実装。`DELETE`ハンドラなし（未対応メソッドのため呼び出すと405） |
| APIルート | `src/app/api/cases/route.ts` | `GET`/`POST`のみ |
| サービス層 | `src/lib/db/repository.ts` | `deleteCase`・`removeCase`等の削除系関数は一切存在しない |
| UI | 案件詳細・一覧ページ | 削除ボタン・削除確認ダイアログ等は存在しない |
| UI（将来言及のみ） | `src/app/(marketing)/security/page.tsx`等 | 「削除方針を明示できるようにします」という**将来予定の文言**が存在するのみで、実装はない |

**結論**: 誤って登録した案件（顧客の機密取引情報を含みうる）を削除する手段が現状一切存在しない。これはテストデータの問題ではなく、プロダクトとしての機能欠落である。

## 2. 実装に必要な変更範囲

### 2-1. データモデル上の課題（重要）

`src/lib/db/schema.ts`を確認したところ、`caseId`で紐づくテーブルは以下の8つ存在する。

```
cases (親)
├─ investigations        (case_id, NOT NULL)
├─ risk_assessments       (case_id = 主キー)
├─ ai_consultations        (case_id, NULL許容)
├─ risk_dimension_scores  (case_id, NOT NULL)
├─ evidence_items         (case_id, NOT NULL)
├─ provider_runs          (case_id, NOT NULL)
└─ generated_reports      (case_id, NOT NULL)
```

**外部キー制約（`references()`）はDrizzleスキーマ上に一切定義されていない**（すべて単なる`varchar`カラム）。そのため、DBレベルでのCASCADE削除は機能しない。案件を削除する場合、アプリケーション側で子テーブルから親テーブルへ向かって手動で順番に削除するトランザクション処理を実装する必要がある。

`ai_consultations`のみ`case_id`がNULL許容（案件に紐づかない一般相談も存在するため）。案件削除時は「レコードごと削除」と「`case_id`をNULLに更新して相談履歴自体は残す」の2案があり、判断が必要（[4章](#4-未確定事項判断が必要)参照）。

### 2-2. 必要な変更ファイル（想定）

| 変更箇所 | 内容 |
|---|---|
| `src/lib/db/repository.ts` | `deleteCaseCascade(caseId)`等の削除関数を追加。8テーブルを子→親の順で削除するトランザクション処理 |
| `src/app/api/cases/[id]/route.ts` | `DELETE`ハンドラを追加。認可チェック（[3章](#3-権限設計)）→ 削除実行 → 監査ログ記録（[5章](#5-監査ログの必要性)） |
| UI（案件詳細ページ） | 削除ボタン、および誤操作防止のための確認ダイアログ（案件名の再入力など） |
| UI（案件一覧ページ） | 一覧からの削除操作（メニュー等） |

## 3. 論理削除（soft delete）と物理削除、どちらを推奨するか

### 推奨: **論理削除（soft delete）を基本とし、一定期間経過後にバッチで物理削除する二段階方式**

**理由**:

1. **本サービスは輸出取引の機密情報を扱う**。誤操作による完全消失は、監査証跡（いつ・誰が・何を登録したか）を失うことを意味し、後日の紛争・監査対応時に「元々何が登録されていたか分からない」という状況を招くリスクが大きい
2. 案件登録には既にAI調査（`investigations`, `risk_assessments`等）の実行履歴が紐づいており、これらは間接的にコスト（AI API呼び出し実績）の記録でもある。物理削除するとコスト分析（`docs/api-cost-estimate.md`参照）の基礎データも失われる
3. ユーザーが「誤って削除してしまった」場合の復旧手段を提供できる
4. 一方で、GDPR的な要請や顧客からの完全削除依頼など、物理削除が必要なケースも将来的に想定されるため、論理削除のみで完結させず、猶予期間後の物理削除（またはユーザー・管理者からの物理削除リクエスト受付）の経路も用意する

**実装イメージ**（今回は方針提示のみ、コード変更は行わない）:
- `cases`テーブルに`deletedAt`（timestamp、NULL許容）カラムを追加
- 通常の一覧・詳細取得クエリは`deletedAt IS NULL`でフィルタ
- 削除操作は`deletedAt`にタイムスタンプを設定するのみ（子テーブルは変更しない）
- 一定期間（例: 30〜90日）経過後、バッチ処理で物理削除（子テーブル含む完全削除）を実行

## 4. 未確定事項（判断が必要）

以下はプロダクトオーナー側の判断が必要な事項として提示する。

3. **復元機能の要否**: 論理削除後、ユーザー自身が「ゴミ箱」的なUIから復元できるようにするか、管理者のみが復元できるようにするか

## 5. 権限設計

### 推奨: **作成者本人 + 管理者の両方に削除権限を付与し、削除操作は必ず監査ログに記録する**

**理由**:

- 作成者本人のみに限定すると、退職・異動等でアカウントが使えなくなった場合に誰も削除できなくなる
- 管理者のみに限定すると、日常的な誤登録の訂正のたびに管理者への依頼が発生し、運用負荷が高い
- 両方に許可しつつ、**誰が削除したかを必ず記録する**ことで、権限の広さによる懸念（悪用・誤用）を監査ログでカバーする

現状のコードには「管理者」ロールの判定ロジックが`ADMIN_EMAILS`環境変数ベースで存在する（`docs/account-migration.md`等で言及）ため、これと整合させた実装が可能と見込まれる。

## 6. 監査ログの必要性

### 推奨: **必須。監査ログなしでの削除機能実装は行うべきではない**

**理由**:

1. 本サービスが扱うのは顧客企業の輸出取引情報という機密データであり、「誰が・いつ・どの案件を削除したか」の記録がなければ、誤削除や悪意ある削除が発生した際に原因追及ができない
2. 論理削除を採用する場合でも、削除操作そのもの（誰が起点になったか）は別途記録しておくべき（`deletedAt`カラムだけでは「誰が」の情報が残らない）
3. B2B SaaSとして企業顧客に提供する以上、将来的にセキュリティ監査・取引先からの説明要求に応える基盤として監査ログは前提条件になりやすい

**実装イメージ**（方針提示のみ）: `audit_logs`のような新規テーブルを設け、`actor_email`, `action`（例: `case.delete`）, `target_id`（case_id）, `created_at`を記録する。将来的に削除以外の重要操作（案件編集、レポート再生成等）にも同じ仕組みを流用できる設計にしておくと拡張性が高い。
